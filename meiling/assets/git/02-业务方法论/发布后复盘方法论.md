# 发布后复盘方法论

## 1. 文档目标

本方法论文档用于定义“内容发布后，应该如何复盘”。

这里说的复盘，不是简单回答“这条内容数据好不好”，也不是看完数据后随口说几句感想，而是回答下面这些问题：

- 这条内容最终结果如何，和原本预期相比怎么样
- 这次结果主要是由选题、内容、平台放大，还是商业承接导致
- 哪些原本判断被验证，哪些被推翻，哪些还不能下结论
- 这次最该保留的做法是什么，最该修正的问题是什么
- 这次结果只影响这一条内容，还是已经影响系统规则
- 这次复盘后，哪些结论应该回写到内容资产、特征资产和系统规则里

这份方法论的主要用途有四类：

- 为 `03-执行流程/发布后复盘流程.md` 提供上位判断边界
- 为 `07-记录表/我方内容库.csv` 中的复盘结论提供统一口径
- 为后续的我方特征验证、组合验证和系统迭代提供归因标准
- 为后续的阶段性经营复盘与账号经营体检提供单篇复盘方法基础

需要明确：

- 复盘不是重复一遍内容分析
- 复盘的目标不是证明自己之前判断对不对，而是让下一轮更准

## 2. 复盘原则

- 先复结果，再复原因：先确认结果表现，再去做归因，不要一开始就带着解释去看数据
- 先看内容任务，再看结果好坏：先明确这条内容原本承担什么任务，再判断结果是否符合预期
- 先区分问题位置，再讨论解决办法：先判断问题主要卡在选题、内容、放大还是承接，再决定改哪里
- 结论必须分强弱：证据充分时才下强结论，证据不足时保留边界
- 单篇问题和系统问题分开：不是每次复盘都要上升到方法论调整
- 复盘必须能回写：没有回写目标的复盘，价值会快速流失
- 复盘服务下一轮：复盘不是总结过去，而是给下一轮内容生产提供更准的输入

## 3. 核心逻辑

发布后复盘的核心逻辑如下：

- 先明确这条内容原本想做成什么
- 再明确它最终实际表现如何
- 再判断结果是好于预期、符合预期，还是低于预期
- 再沿着选题判断、内容兑现、平台放大、商业承接四个方向归因
- 再判断这次是否构成一次我方验证
- 最后决定哪些结论回写到内容实例、特征资产和系统规则中

如果压成一句话，就是：

- `复盘不是复“结果本身”，而是复“目标、结果、原因、回写”这四段关系。`

## 4. 核心要素

### 4.1 总览

| 要素 | 核心问题 | 作用 |
| --- | --- | --- |
| 复盘对象 | 这次到底在复什么 | 先定口径 |
| 复盘基准 | 这次原本想做成什么 | 定义预期 |
| 结果判断 | 最终结果是好于预期、符合预期，还是低于预期 | 定义结论 |
| 归因层级 | 问题主要出在哪一层 | 避免乱归因 |
| 回写规则 | 这次结论该写回哪里 | 让复盘沉淀成资产 |

### 4.2 复盘对象

这一部分解决的是：

- 本次复盘到底在复什么

建议先区分三类对象：

| 对象 | 核心问题 | 常见场景 |
| --- | --- | --- |
| 单篇内容 | 这条内容为什么跑成这样 | 日常发布后复盘 |
| 单个选题 | 这个题值不值得继续做 | 选题方向复盘 |
| 一组内容 | 某一类内容为什么持续强或持续弱 | 阶段性内容复盘 |

需要明确：

- `发布后复盘方法论` 当前以 `单篇内容` 为主
- 但它的结构以后可以上升复用于“题组复盘”和“阶段复盘”

### 4.3 复盘基准

这一部分解决的是：

- 这次复盘不能只看结果，还要先明确“原本想做成什么”

建议在复盘前固定回看下面这些基准：

- 这条内容原本对应哪个 `选题ID`
- 原本目标用户是谁
- 原本核心痛点是什么
- 原本收益承诺是什么
- 原本核心命题和切口是什么
- 原本建议借用哪些特征与组合
- 这条内容原本承担的主要任务是什么

常见任务大致分为：

| 任务类型 | 核心目标 |
| --- | --- |
| 认知进入 | 让更多人愿意点开和认识你 |
| 信任建立 | 让用户觉得你说得有价值、可信 |
| 沉淀动作 | 让用户收藏、关注、评论、私信 |
| 商业承接 | 让用户进入咨询、加微信、成交等更强动作 |

需要明确：

- 如果一条内容原本任务是 `认知进入`，就不能只拿成交看它
- 如果一条内容原本任务是 `商业承接`，就不能只看播放高低

## 5. 结果判断

复盘第一步不是解释原因，而是先判断结果本身。

建议统一分成三类：

| 结果类型 | 定义 | 含义 |
| --- | --- | --- |
| 好于预期 | 实际结果明显超过原本承担的任务要求 | 说明这条内容出现超额成立点 |
| 符合预期 | 实际结果与原本任务基本匹配 | 说明这条内容在当前任务上成立 |
| 低于预期 | 实际结果明显低于原本任务要求 | 说明某一段链路存在明显问题 |

需要明确：

- 这里的“预期”不是情绪预期，而是基于内容任务的业务预期
- 如果预期本身不清楚，这次复盘就只能做弱判断

## 6. 归因层级

发布后复盘时，建议优先沿着下面四层归因：

| 层级 | 核心问题 | 常见表现 |
| --- | --- | --- |
| 选题判断层 | 这个题本身值不值得进入 | 痛点弱、题意弱、切口弱、目标用户不清 |
| 内容兑现层 | 进来以后值不值 | 命题弱、结构弱、解释弱、价值不兑现 |
| 平台放大层 | 内容本身成立，但没有被放大 | 进入不差但分发弱，或分发弱于同类样本 |
| 商业承接层 | 内容有沉淀，但业务动作承接不上 | 私信少、加微信少、咨询弱、成交弱 |

需要明确：

- 一次复盘可能有多个问题，但必须先找主因
- 不要把所有问题都归到“内容不够好”
- 也不要把所有问题都归到“平台不给流量”

## 7. 复盘结论类型

复盘时最终建议输出下面几类结论：

| 结论类型 | 作用 |
| --- | --- |
| 表现结论 | 这次整体结果如何 |
| 原因结论 | 主要问题更偏哪一层 |
| 保留结论 | 哪些做法应该继续保留 |
| 修正结论 | 哪些地方下次必须调整 |
| 验证结论 | 哪些特征和组合被我方验证了 |
| 系统结论 | 是否需要上升到方法论、流程或词典调整 |

需要明确：

- 没有“保留结论”的复盘，容易只看到问题
- 没有“修正结论”的复盘，无法反作用于下一轮
- 没有“验证结论”的复盘，特征资产无法沉淀

## 8. 回写规则

复盘完成后，结论必须分流回写。

建议统一按下面五类回写：

| 回写位置 | 回写内容 | 作用 |
| --- | --- | --- |
| `07-记录表/我方内容库.csv` | 发布数据、复盘总结路径、我方验证结论 | 沉淀单篇内容结果 |
| `选题库.csv` | 发布后结果、复盘状态、阶段判断 | 沉淀选题层判断 |
| `内容特征库.csv` / `内容特征组合库.csv` | 被验证或被修正的特征与组合 | 沉淀特征资产 |
| `07-记录表/我方内容特征验证记录.csv` | 每次我方验证的具体对象、结论和证据路径 | 沉淀验证过程资产 |
| `我方调整候选池.md` | 上升到系统规则的提醒 | 沉淀系统迭代候选 |

需要明确：

- 单篇问题不必每次都写入 `我方调整候选池`
- 只有当某次复盘已经影响“选题、生产、复盘、特征词典、特征组合”的上游规则时，才上升为系统问题

## 9. 标准复盘顺序

讨论一条已发布内容时，建议按下面顺序推进：

| 步骤 | 目标 | 输出 |
| --- | --- | --- |
| 1. 回看原始任务 | 明确这条内容原本想做成什么 | 复盘基准 |
| 2. 盘点最终结果 | 明确实际结果和数据情况 | 结果清单 |
| 3. 判断结果类型 | 明确是好于预期、符合预期还是低于预期 | 表现结论 |
| 4. 沿四层归因 | 找出问题主因更偏选题、内容、放大还是承接 | 原因结论 |
| 5. 判断验证结果 | 明确哪些特征和组合被验证 | 验证结论 |
| 6. 输出保留与修正 | 明确下次继续什么、改变什么 | 调整建议 |
| 7. 执行回写 | 把结论分流回写到系统里 | 资产沉淀 |

一句话说：

- `发布后复盘的顺序是：先定原任务，再看最终结果，再做归因、验证和回写。`

## 10. 与其他文档的关系

- `02-业务方法论/数据分析方法论.md`：定义怎么理解数据及其判断边界
- `02-业务方法论/发布后复盘方法论.md`：定义复盘时如何归因、如何形成结论、如何回写
- `03-执行流程/发布后复盘流程.md`：负责把这份方法论变成实际执行步骤
- `03-执行流程/内容生产流程.md`：提供复盘时要回看的原始终稿与生产结论
- `03-执行流程/选题分析流程.md`：提供复盘时要回看的原始选题定义

需要明确：

- 数据分析回答的是 `这些数据支持什么判断`
- 发布后复盘回答的是 `这次为什么这样、下一步怎么改、该写回哪里`

## 11. 一句话收束

发布后复盘方法论最终要解决的，不是“这条内容跑得好不好”，而是：

- `基于原任务、最终结果和数据证据，判断这次问题主要卡在哪一层，哪些做法要保留、哪些要调整，并把结论稳定回写到系统里。`
